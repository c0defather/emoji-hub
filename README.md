# Emoji Hub

**Эмодзи для всех поколений. С объяснениями.**

> **Демо:** https://emoji-hub-gamma.vercel.app/ **Исходники:** https://github.com/c0defather/emoji-hub

Каталог эмодзи, который отвечает не на вопрос «как называется эта картинка», а на
вопрос «что человек имел в виду, когда мне это прислал». Для каждого эмодзи нейросеть
написала на трёх языках — английском, русском и казахском — четыре вещи:

- нейтральное описание того, что изображено;
- что эмодзи значит, когда его отправляет **миллениал**, и пример такого сообщения;
- что он значит, когда его отправляет **зумер**, и пример такого сообщения.

Разница между поколениями тут не шутка ради шутки: 😏 у миллениала — это флирт
(«Заглянешь ко мне сегодня вечером на кофе? 😏»), а у зумера — сарказм («ну да конечно
так я и поверил 😏»). Ровно из-за таких расхождений люди и понимают друг друга неверно.

Всего получилось 1791 эмодзи × 3 языка = **5373 сгенерированные записи**, лежащие в
Postgres. Поверх них — интерфейс, в котором поиск, фильтры, сортировка и переключение
языка срабатывают мгновенно, без единого запроса к серверу.

| | |
| --- | --- |
| **Стек** | Next.js 16 (App Router), TypeScript, Postgres, Drizzle ORM, Tailwind CSS, Vercel AI SDK |
| **Внешний API** | [emojihub](https://github.com/cheatsnake/emojihub) — вызывается **только с сервера** |
| **Модель** | `google/gemini-3.7-flash` через Vercel AI Gateway |
| **Хостинг** | Vercel, две ежедневные cron-задачи |

**Где я отступил от задания и почему**

*Отдельной «главной с приветствием» нет.* По заданию главная и каталог — две страницы.
Я сделал их одной: сверху приветственный блок с названием и подзаголовком на градиенте,
сразу под ним — поиск и сетка. Причина простая: страница-заглушка, единственная функция
которой — кнопка «перейти в каталог», добавляет пользователю лишний клик и ничего не
даёт. Атмосферу задают оформление и сам контент, а не отдельный экран.

*Языков три, а не один.* Это главное, что я добавил сверх задания. Kazakh и русский
здесь не машинный перевод английского текста, а отдельная генерация: промпт прямо
запрещает транслитерацию и требует писать на языке, а не переводить пословно.

## Быстрый старт

Нужны **Node 20+**, **pnpm** и база **Postgres** (хватит бесплатного тарифа
[Neon](https://neon.tech)). Для генерации описаний понадобится ещё
[ключ Vercel AI Gateway](https://vercel.com/d?to=%2F%5Bteam%5D%2F~%2Fai-gateway%2Fapi-keys).

```bash
pnpm install
cp .env.example .env      # POSTGRES_URL, при желании AI_GATEWAY_API_KEY
pnpm db:migrate           # создать таблицы
pnpm emojis:sync          # забрать 1791 эмодзи из внешнего API (~10 секунд)
pnpm emojis:enrich        # сгенерировать все описания (~28 минут, тратит токены)
pnpm dev                  # http://localhost:3000
```

Единственный долгий шаг — `emojis:enrich`. Полная генерация каталога заняла у меня
~28 минут и примерно 86K входных / 835K выходных токенов при батче в 50 эмодзи и трёх
параллельных запросах. Прерывать её безопасно: запустите заново — продолжит с того же
места, ничего не потеряется и не сгенерируется дважды.

Если хочется просто посмотреть, как это работает, не оплачивая весь каталог:

```bash
pnpm emojis:enrich --limit=10 --once --verbose
```

Проверки, которые я гоняю перед коммитом:

```bash
pnpm typecheck && pnpm lint
```

## Как это устроено

```
emojihub API ──► cron sync (03:00) ──► Postgres ──► cron enrich (03:30) ──► Postgres
                                          │                    ▲
                                          │                    └── LLM через AI Gateway
                                          ▼
                                    GET /api/emojis
                                          │
                                          ▼
                              браузер: одна загрузка каталога,
                              дальше поиск/фильтры/сортировка локально
```

Ключевая деталь: **внешний API никогда не вызывается из браузера**. Пользовательский
запрос вообще не может дойти до emojihub — данные попадают туда только через
серверную cron-задачу, которая складывает их в свою базу. Даже если внешний сервис
ляжет, приложение продолжит работать.

Второй важный момент: тексты генерируются **заранее**, а не в момент открытия страницы.
Иначе каждый просмотр стоил бы токенов и нескольких секунд ожидания.

## Почему именно такой стек

**Next.js (App Router).** Проект состоит из интерфейса, одного JSON-эндпоинта и двух
задач по расписанию. Next.js упаковывает всё это в один деплой: не нужен отдельный
бэкенд, не нужен CORS, не нужен второй пайплайн в CI. Серверные компоненты вдобавок
дают странице эмодзи ходить в Postgres напрямую и рендериться на сервере — то есть без
клиентского запроса, без состояния загрузки и с нормальными метатегами для превью
ссылок. Отдельный SPA плюс API-сервер на таком объёме только удвоили бы количество
вещей, которые надо поддерживать.

**TypeScript.** Эмодзи проходит через четыре превращения: JSON внешнего API →
провалидированный объект → строка в базе → DTO → пропс компонента. На каждом стыке
переименованное поле ломается молча. Типы плюс zod на границе с внешним миром
превращают это в ошибку сборки. Работает не в теории: когда я удалял колонку `group` и
когда добавлял поля с примерами, компилятор сам выдал список всех мест, которые надо
поправить.

**Postgres + Drizzle.** Данные реляционные (эмодзи 1→N переводов), нужны индексы и
агрегаты, а очередь на генерацию — это вообще обычный `LEFT JOIN` (подробнее ниже).
Drizzle я предпочёл Prisma по двум причинам: его запросы выглядят как SQL, поэтому
сложную выборку видно целиком и не приходится выражать её через абстракции ORM; и он
генерирует обычные `.sql`-миграции, которые можно прочитать в диффе перед тем, как
применять к живой базе. Плюс у него нет кодогенерации и отдельного бинарника движка —
для serverless это меньше холодный старт.

**Vercel AI SDK + AI Gateway.** `generateObject` со схемой zod означает, что модель либо
возвращает структуру нужной формы, либо падает с ошибкой. Никакого «распарсим и
понадеемся» и никакой ручной проверки полей. Gateway превращает выбор модели в строку
в переменной окружения, так что попробовать другого провайдера — это правка одной
строки в `.env`, а не новый SDK со своим клиентом и своими ошибками.

**Tailwind.** Интерфейс — примерно десяток компонентов, полноценная дизайн-система тут
избыточна. Утилитарные классы держат оформление рядом с разметкой: читать нужно один
файл, а не прыгать между компонентом и стилями. Три повторяющихся паттерна (`.card`,
`.field`, `.glyph`) вынесены через `@apply` в `globals.css`.

**Ничего для управления состоянием.** Глобального состояния ровно два куска — язык и
избранное. Оба это React-контексты строк на сорок поверх `localStorage`. Redux или
Zustand здесь были бы сложнее, чем то, чем они управляют.

## Как я это делал

Работал в четыре захода, каждый доводил до рабочего состояния перед началом следующего.

**1. Сначала данные, потом интерфейс.** Схема, клиент к emojihub и синхронизация —
всё это проверялось запуском на настоящей базе, когда ни одного компонента ещё не
существовало. Самым неочевидным здесь оказался вопрос идентификатора: внешний API не
отдаёт первичный ключ, а имена эмодзи не уникальны — есть несколько записей, буквально
названных `flag`. В итоге id — это слаг из имени и unicode-кодпоинтов, единственная
комбинация, уникальность которой гарантирована. Ошибись я здесь, и позже пришлось бы
перегенерировать все переводы, так что вопрос стоило закрыть до всего остального.

**2. Пайплайн генерации — сначала как скрипт.** `scripts/enrich.ts` появился задолго до
эндпоинта: промпт надо было итерировать, а делать это на HTTP-ручке дорого и неудобно.
Флаг `--verbose` печатает полный запрос и ответ, `--limit=10 --once` прогоняет десяток
эмодзи. Основная работа на этом этапе была не в коде, а в тексте промпта. Первые версии
выдавали русский, который на самом деле был транслитерированным английским, и казахский,
который был пословной калькой с английской фразы. Сейчас системный промпт явно
запрещает и то и другое, требует кириллицу для казахского и отдельно оговаривает, что
миллениалы пишут с пунктуацией, а зумеры — строчными и без точек. Только когда результат
стал стабильно приличным, та же функция была подключена к `/api/cron/enrich`.

**3. API и интерфейс.** Один эндпоинт, затем каталог, страница эмодзи и избранное.
Решение скачивать весь каталог на клиент принималось здесь — и определило всё
дальнейшее: фильтры, сортировка, переключение языка и избранное стали обычными
операциями над массивом, без запросов и состояний загрузки.

**4. Чистка.** К этому моменту в проекте накопилось заметное количество мусора: демо-
таблица `profiles` из стартера Vercel, шесть API-эндпоинтов, которыми интерфейс не
пользовался, измерение `group`, оказавшееся дубликатом категории, и блок «другие языки»
на странице эмодзи, потерявший смысл, когда переключение языка стало мгновенным. Всё
это было удалено; чтобы найти то, что не видно глазами, я прогнал по репозиторию
[`knip`](https://knip.dev) — он показывает неиспользуемые файлы, экспорты и зависимости.
API сократился с семи эндпоинтов до трёх.

Схема менялась дважды уже после того, как в базе были данные; обе миграции лежат в
`drizzle/` и применяются `pnpm db:migrate`:

| Миграция | Что делает |
| --- | --- |
| `0001_drop_profiles` | Удаляет демо-таблицу из стартера |
| `0002_group_out_examples_in` | Убирает `emojis.group`, добавляет колонки с примерами |

## Решения, которыми я доволен

### Очередь на генерацию — это SQL-запрос, а не очередь

Ни таблицы задач, ни Redis, ни воркера. На вопрос «каким эмодзи нужна генерация»
отвечает `LEFT JOIN`, который считает готовые переводы для текущей версии контента:

```
emojis LEFT JOIN emoji_translations
  ON translation.emoji_id = emoji.id
 AND translation.source_version = emoji.content_version
 AND translation.millennial_example IS NOT NULL
WHERE translation.emoji_id IS NULL
```

Раз очередь выводится из самих данных, а не хранится отдельно, она не может с ними
разойтись. Упал процесс, закончилось время выполнения функции, я нажал Ctrl+C — чистить
нечего: следующий запуск просто задаст тот же вопрос и получит правильный ответ. Именно
поэтому генерация возобновляемая, хотя специально её такой никто не делал.

### Синхронизация, адресуемая по содержимому

Два уровня хешей делают ежедневную синхронизацию почти бесплатной:

- **Хеш всего ответа** внешнего API. Совпал с прошлым разом — задача пишет `unchanged`
  и завершается, не сделав ни одной записи в базу. Так происходит почти каждый день.
- **`source_hash` на каждый эмодзи** показывает, какие именно записи изменились. У
  изменившейся поднимается `content_version` — и её переводы автоматически становятся
  устаревшими для запроса выше.

То есть правка на стороне emojihub доезжает до пользователя сама: синхронизация поднимет
версию, ночная генерация перепишет только затронутые эмодзи.

### Nullable-колонка вместо скрипта дозаполнения

Когда я добавлял примеры сообщений, обе новые колонки я сделал nullable **намеренно**.
`NULL` в примере означает «эта строка написана до того, как примеры появились» — и такая
строка перестаёт считаться готовой в join'е выше. В результате все 1791 эмодзи вернулись
в очередь сами, без разового скрипта и ручного списка того, что надо перегенерировать.
Добавить новое генерируемое поле в этот проект — значит добавить колонку, поле в
zod-схему, строчку в промпт и условие в join. Остальное произойдёт само.

### Ошибка модели и ошибка платформы — разные вещи

У каждого эмодзи есть бюджет попыток, после которого он пропускается, чтобы один
проблемный случай не блокировал всю ночную задачу. Но тратят этот бюджет **только
неразбираемые ответы** — когда модель проигнорировала схему или ответ обрезался.
Закончившиеся кредиты, рейт-лимит и падение провайдера логируются и повторяются в
следующий раз без штрафа, потому что они ничего не говорят о самом эмодзи. Без этого
различия одного протухшего API-ключа хватило бы, чтобы за три ночи пометить весь каталог
как безнадёжный.

### Одна загрузка — дальше всё локально

`lib/use-catalog.ts` один раз на вкладку тянет `/api/emojis?locale=all` в кеш уровня
модуля, за общим промисом, чтобы два одновременно смонтированных компонента не сделали
два запроса. Дальше всё — операции над массивом в памяти:

- **Поиск** идёт по заранее склеенной строке на каждый эмодзи, куда входит вообще всё:
  id, английское имя, категория, сам символ, unicode, HTML-код, а также имя, описание,
  оба значения и оба примера на трёх языках. Несколько слов в запросе — должны совпасть
  все.
- **Сортировка** учитывает язык через `Intl.Collator`, поэтому кириллица сортируется
  по алфавиту, а не по кодам символов.
- **Переключение языка** мгновенное: все три перевода уже в памяти, запроса нет, и
  английский текст нигде не мелькает.
- Фильтры пишутся в URL (`?q=&category=&sort=&dir=`), так что ссылкой можно поделиться,
  а кнопка «Назад» возвращает к прежнему виду. Ввод в поиске обёрнут в
  `useDeferredValue`, чтобы печатать было комфортно, пока перефильтровываются ~1800
  элементов.

### Избранное, которое можно унести с собой

Избранное — это id в `localStorage`, синхронизированные между вкладками через событие
`storage`. Аккаунтов нет, на сервер ничего не уходит — а значит, очистка данных сайта
стирает всё. Поэтому на странице избранного есть **Экспорт** и **Импорт**: экспорт
скачивает небольшой JSON, импорт *дополняет* список и никогда ничего не удаляет, так что
восстановление старой копии не затрёт новые добавления. Парсер принимает любой JSON с
массивом id в поле `favorites` или просто голый массив — файл, написанный руками, тоже
подойдёт.

## Компромиссы

**Скачать весь каталог против запросов на каждое нажатие клавиши.** ~927 КБ в gzip,
отданные сразу, покупают мгновенные поиск, фильтры, сортировку и переключение языка,
один общий ответ, который кеширует CDN, и отсутствие целого класса кода — дебаунсов,
гонок запросов, спиннеров, пагинации. Платим первой отрисовкой и трафиком того, кто
посмотрел один эмодзи и ушёл. Для каталога, который небольшой, публичный, одинаковый
для всех и меняется раз в сутки, обмен выгодный. Для больших, приватных или часто
меняющихся данных решение было бы неверным.

**Генерировать заранее против генерации по запросу.** Генерация в момент открытия
страницы всегда была бы актуальной и не требовала базы, но каждый просмотр стоил бы
токенов и секунд ожидания. Заранее — чтение бесплатное и мгновенное, зато появляется
проблема устаревания, ради которой и сделана механика с `content_version`.

**Большие батчи против одного эмодзи на запрос.** 50 эмодзи одним вызовом заметно
дешевле и быстрее, чем 50 вызовов: системный промпт отправляется один раз вместо
пятидесяти. Риск — один битый ответ теряет весь батч. Компенсируется повторами,
описанной выше классификацией ошибок и явным лимитом выходных токенов на эмодзи: без
него провайдер применяет свой дефолт и молча обрезает JSON посреди объекта, а это
крайне неприятный способ узнать о проблеме.

**Мёртвое поле, оставшееся в хеше.** `source_hash` до сих пор считается вместе с полем
`group`, хотя колонки давно нет. Убрать его — значит разом изменить все 1791 хеш и без
всякой причины отправить каталог на полную перегенерацию. Комментарий в
`lib/emoji-hub/client.ts` объясняет, почему поле парсится, но не сохраняется.

**Удалить неиспользуемый API, а не оставить «на будущее».** Были эндпоинты категорий,
групп, статистики, истории синхронизаций, health-check и одиночного эмодзи. Ни один не
использовался интерфейсом. Оставить — значит поддерживать и документировать публичный
API, которым никто не пользуется. Если он когда-нибудь понадобится, его стоит
спроектировать осознанно, а не собрать из того, что случайно осталось от фронтенда.

**Мягкое удаление вместо жёсткого.** Эмодзи, пропавший из внешнего API, помечается
`is_active = false`, а не удаляется: если он вернётся, оплаченные переводы уцелеют.

**Автотестов нет.** Проверяю `pnpm typecheck`, `pnpm lint`, `knip` и руками на живой
базе. Логика тут в том, что самая рискованная часть системы — недетерминированная
модель, которую юнит-тестами всё равно не покроешь, а времени на тесты детерминированных
частей я не выделил. Это честный пробел, а не позиция; ниже он повторён в списке
проблем.

## Что работает не идеально

**Тяжёлая первая загрузка.** Каталог — ~3.9 МБ JSON, ~927 КБ в gzip. Он кешируется CDN
и грузится один раз на вкладку, но на медленном соединении сетка несколько секунд
показывает скелетон. Примеры сообщений увеличили этот объём примерно на 40%. Правильное
решение — отдавать сначала урезанный индекс (id, имя, категория, символ), остальное
догружать лениво.

**Нет переключателя стилей отрисовки.** Бонус в задании предлагал переключать вид
эмодзи через `htmlCode` / `unicode`. Я сознательно оставил один вид — сам символ:
коды как способ «нарисовать» картинку выглядят хуже, чем глиф, и ломают сетку.
Оба значения всё равно есть на странице эмодзи и копируются одной кнопкой.

**Нет автотестов.** Детерминированные части — вычисление `source_hash`, диффинг при
синхронизации и парсер файла избранного — тестируются легко, и тесты у них должны быть.

**Сгенерированные тексты никто не вычитывал.** Все 5373 записи — вывод модели. Носитель
языка их не проверял, а казахский представлен в обучающих данных заметно хуже
английского и русского, так что именно там качество, скорее всего, самое неровное.
Пожаловаться на плохую запись из интерфейса нельзя — такой кнопки нет.

**Поиск ищет подстроку.** Русский и казахский сильно флективные, поэтому `кошка` не
найдёт `кошки`. Ни стемминга, ни нечёткого поиска, ни устойчивости к опечаткам.

**Позиция прокрутки не восстанавливается.** Сетка догружается порциями по 96 через
`IntersectionObserver`. Если открыть эмодзи и нажать «Назад», окажешься в начале заново
набранного списка.

**Избранное привязано к браузеру.** Очистка данных сайта его стирает, экспорт/импорт —
единственная и полностью ручная страховка.

**Отрисовка зависит от системного шрифта.** На старых системах новые эмодзи могут
показываться пустыми квадратами; картинок-фолбэков нет.

**Названия категорий переведены руками** в `lib/i18n.ts`. Если во внешнем API появится
новая категория, она будет показываться по-английски, пока её не добавят в словарь.

**`/api/emojis` открыт и без рейт-лимита.** Нагрузку принимает CDN (`s-maxage=300`),
никакой другой защиты нет.

**Cron на тарифе Hobby запускается раз в сутки.** Если во внешнем API изменится сразу
много эмодзи, часть останется без свежих текстов до следующей ночи — либо надо
запустить `pnpm emojis:enrich` руками.

## Справочник

### Страницы

| Маршрут | Что делает |
| --- | --- |
| `/` | Приветственный блок, поиск, фильтр по категории, сортировка, бесконечная сетка |
| `/emoji/[id]` | Всё, что известно об одном эмодзи, на активном языке |
| `/favorites` | Сохранённые эмодзи, экспорт и импорт |

### API

`GET /api/emojis` отдаёт каталог. Серверного поиска и фильтра намеренно нет — клиент
держит всё у себя и фильтрует локально.

| Параметр | По умолчанию | Примечание |
| --- | --- | --- |
| `locale` | `all` | `en`, `ru`, `kz`, список через запятую или `all` |
| `limit` | `5000` | 1–5000 |
| `offset` | `0` | Начало страницы |

| Cron-эндпоинт | Описание |
| --- | --- |
| `GET\|POST /api/cron/sync` | Синхронизация с внешним API. `?force=true` — применить заново |
| `GET\|POST /api/cron/enrich` | Один проход генерации. `?limit=`, `?timeBudgetMs=`, `?force=true` |

Оба требуют `Authorization: Bearer $CRON_SECRET` (его шлёт Vercel Cron) либо заголовок
`x-cron-secret`. Вне продакшена, если секрет не задан, проверка пропускается.

### Переменные окружения

| Переменная | Обязательна | Зачем |
| --- | --- | --- |
| `POSTGRES_URL` | да | Подключение к базе в рантайме |
| `POSTGRES_URL_NON_POOLING` | для миграций | Прямое подключение для drizzle-kit |
| `AI_GATEWAY_API_KEY` | для генерации | Не нужен на Vercel с включённым OIDC |
| `CRON_SECRET` | в продакшене | Защита `/api/cron/*` |
| `EMOJI_ENRICHMENT_MODEL` | нет | По умолчанию `google/gemini-3.7-flash` |
| `EMOJI_ENRICHMENT_BATCH_SIZE` | нет | Эмодзи на один вызов модели, по умолчанию `8` |
| `EMOJI_ENRICHMENT_CONCURRENCY` | нет | Параллельных вызовов, по умолчанию `3` |
| `EMOJI_ENRICHMENT_MAX_ATTEMPTS` | нет | Попыток до пропуска эмодзи, по умолчанию `3` |
| `EMOJI_ENRICHMENT_DEBUG` | нет | `1` — логировать промпт и ответ целиком |

### Скрипты

| Команда | Что делает |
| --- | --- |
| `pnpm dev` / `pnpm build` / `pnpm start` | Next.js |
| `pnpm typecheck` / `pnpm lint` | Статические проверки |
| `pnpm emojis:sync [--force]` | Синхронизация из CLI |
| `pnpm emojis:enrich [--limit=N] [--once] [--batch-size=N] [--concurrency=N] [--force] [--verbose]` | Генерация, пока есть необработанные |
| `pnpm db:generate` / `pnpm db:migrate` / `pnpm db:studio` | Drizzle Kit |

### Модель данных

- **`emojis`** — строка на каждый эмодзи из внешнего API. `source_hash` ловит изменения
  конкретной записи, `content_version` инвалидирует её переводы, `is_active` помечает
  эмодзи, пропавшие из источника.
- **`emoji_translations`** — ключ `(emoji_id, locale)`: имя, описание, оба поколенческих
  значения с примерами, модель-автор и версия контента, для которой текст сгенерирован.
- **`sync_runs`** — журнал синхронизаций: счётчики, длительность, хеш и ошибки.

### Расписание

`vercel.json` регистрирует синхронизацию на 03:00 UTC и один проход генерации на
03:30 UTC. Одного прохода хватает на эмодзи, изменившиеся за сутки; первичная генерация
всех 1791 запускается один раз из CLI.

### Логи генерации

Каждый вызов модели пишет строку в stdout — в рантайм-логи Vercel для cron и в терминал
для CLI:

```
[enrich] request model=google/gemini-3.7-flash batch=50 emojis=[snail-u-1f40c, …]
[enrich] response batch=50 results=50 tokens=2226/19592 took=79.1s
[enrich] failed batch=8 took=1.5s emojis=[…] reason=…
```

Если ответ не разобрался, дополнительно логируется сырое тело — иначе не отличить
обрезанный ответ от модели, проигнорировавшей схему. Флаг `--verbose` (или
`EMOJI_ENRICHMENT_DEBUG=1`) печатает промпт и ответ целиком для каждого вызова.
